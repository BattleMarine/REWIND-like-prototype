# v1 실험 분기와 검증 의사결정 기록

## 실험 분기 트리

```text
v1 — 1,000 train 페어에서 REWIND 기반 구조·실행 연결
│    각 1epoch: 연결은 동작, 2D 중앙 집중·3D 형태 축소 관찰
│
├─ v1.1 — 같은 1,000페어에서 학습량 확대
│  │       각 10epoch: 2D 개선, 3D 형태 축소 지속
│  │
│  └─ v1.4 — 한 train 클립 + GT 2D + hand용 GT 상체
│             정답 조건에서도 3D 형태를 학습할 수 있는지 분리 진단
│             [A100 각5,000update 완료 / 동일클립 GT조건 형태복원 확인]
│             ├─ v1.5 제안 ← v1.2 예측 모델과 결합: 같은클립 GT→예측 조건 분리
│             │             [설계만 / 구현·새 학습 미시작]
│             ├─ 복원 성공 → 저장 모델의 train 복원·조건 교체 평가(제안)
│             │             → 학습량과 입력 조건의 통제 학습(제안·미실행)
│             └─ 미수렴    → 최적화·좌표·조건·loss·sampling 원인 재검토
│
├─ v1.2 — ArchVis 전체 train으로 데이터 규모 확대
│          20,888 train + 고정 validation 2,236
│          [각10epoch 완료 / 2D·body 개선, 손 축소 잔존 / train2프레임 시각화 확인]
│
└─ v1.3 — 다른 시나리오를 추가해 다양성·일반화 확인
           [보류 / 새 수집·혼합·학습 미승인]
```

화살표는 **질문과 가설의 분기 관계**다. 체크포인트를 이어 학습한다는 뜻이나 버전 번호순 실행 의무가 아니다. v1.4는 v1.1의 실패 양상에서 나온 진단이며, v1.2 완료를 기다릴 필요가 없다. 트리의 후속 후보는 실행 승인이 아니다.

기록 기준: 2026-11-12. 앞으로 새 테스트를 설계하거나 결과를 검토할 때 **이 문서와 상단 트리를 함께 갱신**한다. 전용 실행 문서는 설정·소스·산출물 pin을, 이 문서는 분기 이유·가설·판정과 후속 결정을 관리한다. 과거 판단은 삭제하지 않고 날짜와 새 근거를 덧붙인다.

## 1. 공통 목표와 용어

목표는 실제 stereo RGB에서 몸과 손의 3D 자세를 추정하고, 이후 동영상에서도 확인할 수 있는 미니 프로토타입이다. 현재는 화면 UI보다 학습 모델의 입력·복원 능력 검증을 우선한다. 학습 코어와 화면 프론트를 분리하며, 여기서 frontend는 **신경망 2D 관절 추정기**를 뜻한다.

v1.x는 실험 분기 이름이고 M0~M6는 로드맵의 개발 단계다. v1.4 완료가 M4 증류 완료를 뜻하지 않는다. 현재 분기들은 주로 M0 데이터와 M2/M3 teacher의 실제 학습 문제를 다룬다.

- 페어는 동일 sequence/frame의 좌우 RGB와 대응 pose를 뜻한다. 1,000페어를 반복해도 고유 데이터 수는 증가하지 않는다.
- Epoch는 선택 학습 집합을 한 번 사용하는 단위다. 서로 다른 규모·batch의 epoch 수만으로 학습량을 비교하지 않는다.
- Update는 optimizer가 파라미터를 갱신한 횟수다. 50프레임 clip 하나가 50번의 update를 뜻하지 않는다.
- GT 조건은 정답을 입력으로 주는 oracle 진단이다. RGB만으로 동작하는 실제 추론과 구분한다.
- 단일 클립 overfit은 의도적으로 훈련 표본을 외우게 하는 검사다. 일반화 성능을 검증하는 시험이 아니다.

## 2. v1: 구조 재현과 실제 실행의 출발점

### 설계 목적

v0의 단일 프레임 중심 비교 모델에서 나아가, 1,000페어 규모를 유지하면서 REWIND 기반 2D frontend·causal body diffusion·body–hand cascade의 실행을 연결한다. 기존 v0 표본은 50프레임 연속 구간이 없어 연속 구간 중심의 별도 subset을 구성했다. v0와 v1의 차이를 모델 구조만의 효과로 해석하지 않는다.

실제 timestamp·stereo 시간 동기·원본 motion 독립성은 확인되지 않았다. 사용자 승인으로 명목 25FPS와 frame-key stereo 대응 가정을 명시한 V1-DIAGNOSTIC-001을 별도로 실행했다. Velocity·foot loss는 사용하지 않으며 엄격 검증 경로는 보존했다.

### 관찰과 남은 질문

A100에서 frontend/body/hand 각 1epoch, 각각 500/20/20 update를 완료했다. Frontend 참고 validation 오차는 307.733px, body MPJPE는 543.357mm, hand global은 551.690mm였다. 학습·저장 연결은 동작했지만 형태 복원은 부족했다.

이후 소수 이미지의 예측과 raw tensor에서 2D 중앙 집중·3D 뭉침을 확인했다. 따라서 다음 질문이 생겼다.

1. 같은 데이터를 더 학습하면 개선되는가? → v1.1
2. 데이터 규모와 동작 범위를 넓히면 개선되는가? → v1.2
3. 다른 시나리오가 일반화에 도움이 되는가? → v1.3 후보

근거: [v1 계획](V1_REWIND_PLAN.md), [실제 1epoch 결과](V1_DIAGNOSTIC_001_RESULTS.md), [당시 원인 진단](V1_COLLAPSE_DIAGNOSIS.md).

## 3. v1 → v1.1: 같은 데이터에서 학습량 확대

### 가설과 통제

초기 teacher는 모델별 20update에 불과했으므로 학습 부족을 우선 의심했다. 동일 train 1,000페어·20개 연속 50프레임 clip을 유지하고 frontend/body/hand를 각각 10epoch로 늘렸다. 모델 구조·기본 LR·좌표·loss·seed·validation 조건을 유지하고 새 run으로 시작했다.

다만 frontend도 함께 학습량이 늘어나므로, v1 대비 teacher 성능 변화에는 **teacher의 추가 학습과 2D 입력 변화가 함께 포함**된다. 순수한 3D update 수의 효과만 분리한 실험은 아니다. 모델별 best checkpoint의 의존성을 따라야 하며 같은 epoch 번호의 모델을 임의 조합하지 않는다.

### 실제 관찰

첫 10epoch 실행은 완료 로그를 확보했으나 모델 ZIP 미회수로 가중치 검토가 불가능했다. 이후 T4 재실행은 모델을 회수했다. 두 실행을 같은 결과로 합치지 않는다.

| T4 재실행 지표 | epoch 1 | best | epoch 10 |
| --- | ---: | ---: | ---: |
| Frontend, 화면 안 2D 오차 | 307.509px | 214.841px (e9) | 215.483px |
| Body MPJPE | 543.158mm | 484.793mm (e9) | 549.247mm |
| Hand global MPJPE | 563.272mm | 514.854mm (e8) | 565.974mm |

Frontend 첫 32 validation 프레임의 정규화 heatmap entropy는 0.9936에서 e9의 0.8253으로 감소했다. 2D 위치 구분은 일부 학습됐다. 하지만 body best의 평균 뼈 길이는 13.274mm로 GT 208.353mm보다 훨씬 작고, hand best도 2.329mm로 GT 25.782mm보다 작았다.

각 teacher는 10epoch에도 **200update**다. Frontend 5,000 + body 200 + hand 200 = 총 5,400update이며, 전체 약 97분에는 입력 처리·평가·저장이 포함된다. 긴 wall-clock을 충분한 3D 학습의 증거로 쓰지 않는다.

### 판정과 분기 이유

“10epoch 확대가 2D 중앙 집중을 완화했다”는 근거는 있다. “3D 형태 복원이 해결됐다”는 근거는 없다. 마지막 epoch 악화만으로 과적합을 확정하지 않는다. train에서 같은 clip을 잘 복원하는지, sampling 변동과 조건 입력이 어떤 영향을 주는지도 확인해야 한다.

이에 데이터 확대만 기다리기보다 **작은 한 클립과 정답 조건에서 3D가 학습 가능한지**를 먼저 분리하는 v1.4로 분기했다.

근거: [첫 실행과 미회수 한계](V11_EPOCH_EXPANSION_RESULTS.md), [T4 재실행·시각화](V11_CUDA_RERUN_RESULTS.md).

## 4. v1 → v1.2: ArchVis 전체 train 확대

### 목적과 선택 과정

1,000페어의 제한된 동작·자세 범위가 학습과 일반화를 제한한다는 가설을 검토한다. 사용자는 절반과 전체의 비용 비교를 요청한 뒤 **ArchVis 전체 train**을 선택했다. 초기 전체 10epoch 약 11.2시간·캐시 약 54GB 추정은 이전 A100 pilot의 외삽이며 준비 비용과 short/tail 처리 비용이 빠져 있어 확정 비용이 아니다.

고정 목록은 train 20,888·validation 2,236페어다. 새로운 데이터의 RGB/pose·좌우 대응·카메라·split을 검사하고 기존 validation과 test 분리를 유지한다. 파일 감사가 통과해도 학습 완료나 모델 개선을 의미하지 않는다.

### 현재 진행과 해석

구버전 감사는 시간 상한에서 9,678페어 카운트만 남겼고 안전한 재개 근거가 부족했다. 완료 페어 journal·복원 기능을 추가한 새 실행은 4,921/23,124페어 기록을 회수했으며 로컬 복원 검토를 통과했다. 두 수치를 합산하지 않는다. 후속 실제 Drive 재개에서 기존 4,921페어를 재사용하고 7,498페어를 추가해 12,419페어까지 전진했다. KeyboardInterrupt 후 자동 보관본의 이전 journal prefix와 고정 소스 복원을 검증했다. 당시 남은 10,705페어를 2026-11-12 후속 호출에서 완료했다. 최종 manifest 23,124행과 journal의 정확한 일치 및 고정 소스 복원을 root가 검증했다. 파일 감사는 완료됐지만 전체 학습은 아직 남아 있다. 재개 기능의 성공을 모델 성능 개선으로 해석하지 않는다.

완전한 50프레임 train 구간만 사용하면 14,050프레임이므로 나머지 short/tail을 숨겨 누락하지 않아야 한다. 전체 프레임 coverage와 padding mask를 학습 전에 검증한다.

### 검증 질문

- 같은 validation·관절·평가 coverage에서 예측이 좋아지는가?
- 데이터 증가에 따라 update 수도 늘어난 효과와 다양성의 효과를 구분할 수 있는가?
- 동일 update 비교와 동일 epoch 비교를 각각 어떤 목적으로 보고하는가?
- 준비·학습·평가·보관 시간을 분리했을 때 비용을 감당할 수 있는가?

v1.2 준비는 v1.4와 병행할 수 있다. 다만 v1.4 미수렴 상태에서 확대 학습이 붕괴를 해결할 것이라고 보장하지 않는다. 실제 확대 학습 설정과 비교 예산은 고정 인계에서 확정한다.

근거: [규모·비용 설계](V1_BRANCH_EXPERIMENTS.md), [구버전 감사](V12_FULL_AUDIT_RESULTS.md), [완료 기록·재개](V12_AUDIT_RESUME.md).

## 5. 원인 가설: 확인한 사실과 아직 모르는 것

| 가설 | 현재 근거 | 해석의 한계·검증 방향 |
| --- | --- | --- |
| 흐릿한 2D heatmap의 평균이 중앙으로 모임 | 좌표는 공간 확률의 기댓값이며 초기 entropy가 거의 최대 | argmax 교체만으로 해결되지 않았고 v1.1에서도 정확도 부족 |
| 3D 학습량 부족 | v1은 모델별 20, v1.1은 200update | update를 늘리면 반드시 해결된다는 증거는 없음 |
| 관절별 특징보다 공통 카메라 조건에 의존 | 이전 1epoch·두 표본에서 2D 교환보다 카메라 교환의 출력 변화가 큼 | v1.1에서 재검증하지 않았으며 카메라 변환 오류의 증거는 아님 |
| 약한 2D가 3D를 망침 | 실제 2D 오차가 큼 | 이전 GT xy 치환만으로 3D가 회복되지 않아 단독 원인 설명은 부족 |
| Body 오류가 hand에 전달 | 예측 상체·손목으로 hand global을 복원 | 손 local 형태도 축소되어 hand 자체의 학습 문제를 배제 못 함 |
| 단위·좌표·loss·sampling 구현 문제 | 일부 단위·복원·관절 순서·유한값 검사는 통과 | 모든 경로의 정확성을 증명한 것은 아니며 미수렴 시 재검토 |
| 데이터 부족·과적합 | 고유 데이터와 동작 범위가 작음 | train 암기 능력 확인 없이 과적합을 원인으로 확정하지 않음 |
| T4 또는 시각화만의 문제 | 실제 update가 수행됐고 raw tensor와 clip 평가에서도 형태 축소 | GPU 속도·T1 추론 한계는 별도이며 붕괴의 직접 원인 근거는 없음 |

이전 1epoch 진단은 불연속 두 프레임을 각각 T1로 처리했고 GT2D는 xy만 교체했다. 현재 v1.1 전체에 대한 완전한 oracle 실험으로 확대 해석하지 않는다. 과거 성분별 RMS와 새 Euclidean RMS spread는 정의가 달라 수치를 직접 비교하지 않는다.

## 6. v1.1 → v1.4: 한 클립의 GT 조건 3D 암기 진단

### 사용자 결정과 질문

2026-11-11 사용자가 한 학습 클립에 GT 2D·GT 상체를 넣고 충분히 학습하여 3D 형태가 만들어지는지 확인하는 실험을 **v1.4**로 명명했다. 2026-11-12 구현·로컬 검증을 마쳤으며 실제 학습 결과는 없다. 세부 실행 설정은 [v1.4 계약](V14_ORACLE_OVERFIT.md)을 따른다.

핵심 질문은 “RGB 인식 오류와 복잡한 데이터 분포를 줄였을 때, 현재 3D 구조·손실·sampling 경로가 하나의 실제 동작을 학습할 수 있는가?”다. 여러 변수를 줄인 진단 조건이므로 v1.1 대비 개선량을 한 원인의 효과로 바로 귀속하지 않는다.

### 입력과 학습 설계

- 기존 감사된 train 1,000페어 안에서 연속 50프레임 한 클립을 고정한다. 같은 클립으로 학습·진단하며 validation/test를 학습에 섞지 않는다.
- Body에는 GT 2D와 카메라를 제공한다. Body 정답 3D를 conditioning 입력으로 직접 넣지 않는다. 확산 학습의 noisy target은 기존 학습 계약에 따른다.
- Hand에는 GT 2D와 GT 상체를 제공한다. GT 손목으로 전역 위치를 붙인 결과와 손목 상대 local 오차를 구분한다.
- GT 2D의 좌표·validity·confidence 의미를 명시한다. 누락값과 화면 밖 관절을 구분하고 유효한 화면 밖 좌표를 임의 clamp하지 않는다.
- 기존 teacher 구조·좌표 단위·target scale·기본 loss·LR를 유지한다. Frontend 학습과 전체 validation은 생략하고 한 클립의 변환된 입력을 재사용한다.
- 새 초기화·고정 seed로 시작한다. 기존 v1.1 checkpoint의 이어 학습과 혼동하지 않는다.

개발 설계안은 body/hand 각각 5,000update, 0/200/1,000/5,000 시점 비교다. 호출 2시간·종료 여유 120초, 100update마다 checkpoint, run 2GiB·회수 1GiB의 유한 예산을 제안했다. 선택 클립·정확한 pin·코드·수치·중단 조건은 로컬 검토 후 전용 실행 문서와 테스트 인계에서 고정한다. 이 수치를 실제 수행 결과나 충분한 수렴 보장으로 기록하지 않는다.

## 8. 공통 운영·증거 보존과 문서 갱신 규칙

학습은 지원되는 CUDA GPU를 허용하고 실제 GPU·VRAM·precision·batch·입력 크기를 기록한다. A100은 추후 추론 레이턴시 비교 조건이다. 준비/학습/평가/보관의 wall-clock과 처리 수를 분리하며 중첩 계측을 합산하지 않는다.

실험별 입력 manifest·코드 revision·config·seed·checkpoint·결과 경로를 분리한다. 정기 checkpoint에는 optimizer·scheduler·scaler·RNG·cursor를 보존하고 종료/실패 시 결과 보관을 준비한다. 브라우저 단절과 VM 종료는 다르며 자동 종료 처리가 VM 강제 종료에서도 실행된다고 보장하지 않는다. [결과 보관 계약](RESULT_RETENTION.md)을 따른다.

향후 테스트마다 다음 항목을 **같은 문서에 추가·갱신**한다.

1. 상단 트리: 부모 실험, 분기 이유, 현재 상태, 다음 분기 조건.
2. 결정: 날짜, 사용자 승인 범위, 제안/확정/보류 여부.
3. 설계: 질문·가설, 변경 변수, 유지 조건, 비교 기준, 데이터·관절·좌표·평가 coverage.
4. 실행: 전용 계약 문서 링크, 고정 소스/입력/예산, 중단·재개·회수 방법. 미확정 값은 미확정으로 남긴다.
5. 결과: 실제 관찰과 수치·근거 파일, 실패·미실행 항목, 기존 가설을 지지/반박하는 범위.
6. 다음 판단: 진행·수정·보류 사유와 아직 승인되지 않은 후속 후보.

전용 문서와 수치가 바뀌면 여기의 요약도 정합성을 확인한다. 계획→구현→로컬 검증→사용자 실행→결과 검토를 구분하고 문서 수정만으로 상태를 올리지 않는다. 개발은 디벨로퍼, 코드 검토·로컬 커밋은 root, 사용자 Colab 안내와 결과 취합은 이 프로젝트의 테스트 세션이 맡는다. 고정 인계 전 새 실험을 반복 실행하지 않는다.

### 2026-11-12 v1.2 전체 학습 연결과 시험 설계

사용자가 완료된 감사 결과로 학습을 시작하도록 테스트 세션에 인계할 것을 요청했다. 데이터 확대가 형태 축소를 개선하는지 확인한다는 가설은 유지한다. 원본 파일 감사를 다시 실행하지 않고 고정 manifest로 train20,888·validation2,236을 연결한다. 시간 동기·motion 독립성은 여전히 미확인이며 명목25FPS와 참고 validation을 명시한다.

Frontend는 전체 train을 사용하고 teacher는 완전281·짧은156·tail127개, 총564clip으로 실제20,888frame을 중복 없이 사용한다. 미래/다른 sequence로 채우지 않는 post-padding과 mask를 적용한다. 기존 per-clip valid-joint 평균을 유지하므로 frame별 균등 가중 실험은 아니다. Teacher validation은 기존29clip/1,450frame이며 제외786frame을 보고한다. 모델·LR·precision·seed·각10epoch를 유지하되 데이터 수 증가로 총115,720update가 된다. 동일epoch와 동일update 비교를 구분하고 단계별 비교 checkpoint를 남긴다.

시험 순서는 준비1청크의 원본 변환·hash 확인, 고정 예산 내 나머지 입력 준비, GPU20update pilot, 그 checkpoint에서 고정10epoch까지 유한 호출로 재개다. Pilot은 frontend 연결만 확인하며 teacher 수렴을 입증하지 않는다. 신규 입력 캐시는 약8.47GiB 이미지 tensor와 metadata로 구성하고 사용자 수행 셀로 Drive에 보존한다. 전체 준비 최소7호출과 결과 보관 비용을 별도로 기록하며 실패 시 설정/예산을 자동 확대하지 않는다.

판정은 운영 성공(coverage·재개·보관·유한 loss)과 모델 개선(기존 분기 대비2D오차·3D형태·시간변화)을 분리한다. 실제 준비·CUDA·Drive 결과는 아직 없다. v1.4 oracle 진단과 v1.3 보류 상태는 유지한다. 상세 실행 조건과 로컬 검증은 [v1.2 학습 연결](V12_TRAINING_CONNECTION.md), 고정 소스·notebook·입력 pin은 배포 receipt/TEST_HANDOFF.md를 따른다.


### 2026-11-12 v1.4 실제 준비 실패
